The bid-link card — what a shared request looks like when it arrives

A renter shares a request with a supplier and the supplier gets a bare URL, so the renter retypes the request underneath it — by hand, in capitals, at 17:37. Every line he types is already a field on the request. This card carries them instead, in five rows, and the fifth one turns every share into an invitation to join.

Subcategory · size · operator
What machine, how big, and whether it comes with a man. From the taxonomy's subcategory and measurement, the operator term, and numberOfUnits for the count. Replaces the renter's subject line, which today is his own reference and a guess at the equipment name.

City · duration, start → end
Where and for how long. The site's city — not the full address, which a supplier does not need to price and should not have before he bids. Duration from the basis and dates, with extendable when set. Replaces “Duration : 1Month & extendable”.

Mobilisation · demobilisation
Who moves the machine, each way. From deliveryToSite and the return party. Replaces “Mob by & demob By Supplier”. Two rows in the card, one column in the image — the two are almost always the same party, so the image pairs them and the card keeps them apart.

Food · accommodation & transport · fuel
Three rows, not one. The app already splits them — fatFood and fatAccommodationTransport are separate fields, because a renter who feeds the operator does not necessarily house him. Then fuelResponsibility with fuelType. Replaces “DIESEL Is Sajco Scope” — and being a field rather than a sentence, it cannot say diesel while the request says petrol.

Get the app
Every shared request becomes an invitation. A supplier bidding through the form is off platform by definition, and this is the moment he is most likely to join — he is already working. The image, and the source domain
880×320, generated by /bid/[token]/og. This is not a thumbnail of a document — it is the card itself. In WhatsApp, Apple Mail and Slack the image is nearly all the recipient sees, so it carries the request's own facts rather than a branded picture. The generic image survives only as the fallback for a request we cannot read. WEB.MOEDATECH.NET is the trust line: it says where the link goes.

B · HOW TO BUILD IT — ONE DATA SOURCE, TWO RENDERINGS

Shared · the preview payload OPEN

Both renderings read the same place. Today it answers prose; it has to answer fields.
•
Today the preview returns { title, description, imageUrl, url }, and the card reverse-engineers the details by splitting the description on a separator and guessing whether each part is a location or a rental basis.
•
Five rows cannot survive that. The payload becomes fields: subcategory, measurement, operator, units, city, basis, start, end, extendable, mob, demob, fat, fuel, fuelType, closesAt. Then both renderings format rather than parse.
•
imageUrl is empty in production. Found against a real token, 2026-09-01. The web now falls back to its own og route instead of the generic file — so this is no longer blocking, but the field should still be filled or dropped deliberately.

Rendering 1 · the image BUILT

880×320 from /bid/[token]/og. Works in production today; it needs the two new lines and the app line.
1
Headline, then the city-and-duration line, then two labelled pairs: mob·demob and FAT·fuel.
2
The app line is text, not a link — nothing in a picture is clickable. It is a reminder; the real link lives in the card.
•
No button. The whole card is already the link, so a button inside it is a second thing to aim at that does the same job — and in the image it is a picture of a button, which teaches a supplier to press something that cannot be pressed. The closing date takes its place.
3
Arabic mirrors the layout and keeps the code, the dates and the count left-to-right. The renderer honours direction: rtl for text but not for flex, so the mirroring is explicit.

Rendering 2 · the HTML card BUILT NEEDS ROWS

440px from bidCardHtml.ts, mirrored by renderBidLinkCard() in backend-admin. Table-based with inline styles, because Outlook ignores flex and most clients strip a <style> block.
1
It gains four term rows and the app line. A row appears only when the request carries it — never “Fuel: —”, because an empty row teaches a supplier to skim the block, and then he skims the row that mattered.
2
Gmail never unfurls a pasted URL, by design — it will not fetch the page. The only way this card reaches Gmail is on the clipboard as text/html, which copyBidLink already writes alongside the plain URL.
3
The two renderings must never disagree. Whatever the image cannot hold appears in the card; nothing in the card contradicts the image.

Who sends it OPEN

The original spec assumed Moedatech sends the mail. For a renter sharing his own request, that decision went the other way.
•
Decided: the share leaves from the renter's own address by mailto:, recipients in BCC. Replies reach him because it is his email.
•
The cost: mailto: cannot carry HTML, so the server cannot bake the card in. The renter gets Copy the message, which puts the card on the clipboard for a Gmail paste, and clients that unfurl do the rest.
•
Still open: whether an app-sent variant should exist. backend-admin already renders this card into mail it sends, so that path costs nothing but the from-address.
C · WHAT STAYS OUT, AND WHY
—
Hours, nationality, certificates, night shift, overtime, SLA, payment
Each is a question the bid form asks structurally, and gets back as data instead of prose. Putting them in the card would be asking twice and reading once. The renter's own note still rides above the button for anything the request does not model.
BY DESIGN
—
The full site address
The city is enough to price. The exact location is on the request once a supplier is in it — a card is scraped without auth, and a link forwarded twice should not put a customer's yard on a stranger's screen.
CONFIRM
—
“Please mention the model year and brand”
The renter typed this in capitals because he had no other way to ask. It is the year term and the form's own make and model fields — set the term and the form asks for him, and the answer comes back comparable instead of buried in a reply.
